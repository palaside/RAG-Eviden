# 📖 DATA_SEMANTICS: คำอธิบายความหมายและพฤติกรรมของข้อมูล (Data Semantics & Schema Guide)

เอกสารนี้อธิบายความหมายของฟิลด์ข้อมูล, กฎการประมวลผลทางการเงิน, ลำดับการสร้าง ID, และวิธีการแยกแยะระหว่าง **ข้อความ OCR บริสุทธิ์** กับ **ข้อความที่เกิดจากการวิเคราะห์หรือเขียนไว้ล่วงหน้า** ในโปรเจกต์ `ชวกม.2` เพื่อความโปร่งใสในการประเมินทางเทคนิค

---

## 1. คำนิยามสถานะการตรวจสอบ (Data Validation States)

ในระบบการตามรอยหลักฐาน มีการจำแนกสถานะของแต่ละองค์ประกอบข้อมูลไว้ดังนี้:

| สถานะ (Status) | คำจำกัดความ (Definition) | เกณฑ์การตัดสินในโค้ด (Trigger Criteria) |
| :--- | :--- | :--- |
| **อ่านได้ (Readable / Extracted)** | ระบบ OCR สกัดค่าตัวเลข วันเวลา หรือรหัสธุรกรรมได้ตรงและมีข้อมูลปรากฏในแคช | Regex ตรวจพบแพทเทิร์นชัดเจน เช่น วันที่ `DD/MM/YY`, เวลา `HH:MM`, ยอดเงิน `X,XXX.XX`, หรือ Ref ID ครบหลัก |
| **ไม่แน่ชัด (Ambiguous / Incomplete)** | สกัดข้อความได้บางส่วน แต่ข้อมูลสำคัญไม่สมบูรณ์ (เช่น เวลาแหว่ง หรือยอดเงินไม่ระบุทศนิยม) | พบบิตข้อความแต่ Regex ไม่สามารถแปลงเป็นประเภทข้อมูลที่สมบูรณ์ได้ |
| **ขัดกัน (Conflict)** | ยอดเงินหรือเวลาในภาพแชทขัดแย้งกับสลิปที่แนบมา หรือชื่อบัญชีไม่ตรงกับข้อความที่กล่าวอ้าง | ยอดเงินในแชทระบุขอ 2,000 บาท แต่สลิปโอนจริงเป็น 1,500 บาท หรือชื่อผู้รับในสลิปเป็นบุคคลอื่น |
| **ไม่พบ (Not Found / Null)** | ภาพนั้นไม่มีสลิป, ไม่มีตราเวลา, หรือไม่มีตัวเลขธุรกรรม | ฟิลด์ระบุค่า `"-"` หรือ `has_slip: false` เช่น ภาพบทสนทนาบริบทที่หลุดเข้าไปในโฟลเดอร์สลิป |
| **ยืนยันโดยผู้ใช้ (User Confirmed)** | ข้อมูลที่มีการตรวจสอบและยืนยันโดยมนุษย์ (Human-in-the-Loop) | เช่น รายการบัญชีใน `KNOWN_ACCOUNTS` และชุดเหตุการณ์ 30 กรรมใน `build_court_dossier_smart_cropped.py` |

## 2. กฎการนับยอดเงินและการป้องกันสลิปซ้ำ (Deduplication & Anti-Double-Counting Rules)

1. **การกรองไฟล์ภาพซ้ำระดับไบนารี (Binary Hash Deduplication):**
   - รัน `hashlib.md5(file_bytes).hexdigest()` บนภาพทุกภาพในโฟลเดอร์นำเข้า
   - หากค่า Hash ตรงกัน ระบบจะตั้งไฟล์แรกเป็น **Master Node** และไฟล์ที่เหลือจะถูกจัดเป็น **Duplicate Record** ซึ่งจะไม่ถูกนำไปประมวลผลซ้ำในสายพานหลัก
2. **การป้องกันการนับยอดเงินซ้ำซ้อน (Anti-Double-Counting in Agent 2):**
   - บัญชีของผู้เสียหายเอง (เช่น บัญชีโอนคืน `XXX-X-XX452-9` นาย ณัฐชัย รักษาวงศ์) จะถูกกรองออก ไม่นำมารวมเป็นยอดความเสียหายของจำเลย
   - หากสลิปใบเดียวกันถูกส่งซ้ำในห้องแชทหลายครั้ง ระบบอิงจากรหัสอ้างอิงธนาคาร (Ref No) หรือ Hash ภาพ เพื่อให้นับความเสียหายเพียงครั้งเดียว
3. **การจัดการกรณีไม่ทราบยอด ไม่ทราบเวลา หรือ Ref หาย:**
   - ใน `agent2_slip_miner.py`:
     ```python
     if recipient == '-' and not has_slip_marker:
         recipient = 'ภาพสนทนาบริบท (ไม่มีสลิปโอนเงิน)'
         amount = '-'
         ref_no = '-'
     ```
   - ระบบจะ **ไม่เดายอดเงินเอง** และไม่ใส่เลขสุ่ม หากอ่านไม่ได้จะบันทึกเป็น `"-"` และกำหนดสถานะเป็น *ภาพสนทนาบริบท*

## 3. วิธีแยกแยะระดับของข้อความ (Data Provenance Tiers)

ในการประเมินความเข้ากันได้ ผู้ประเมินต้องแยกแยะ 3 ระดับข้อมูลต่อไปนี้:

1. **ข้อความ OCR ตรงจากภาพ (Raw OCR Text):**
   - แหล่งที่มา: ฟิลด์ `raw_snippet` ใน `MASTER_SSOT_OCR_DATA.json`, ฟิลด์ `full_snippet` ใน `BENEFICIARY_TRANSACTION_RECORDS.json`, หรือค่าใน `chat_ori_cache.json`
   - ลักษณะ: จะพบคำเพี้ยนหรือเครื่องหมายขยะของ OCR ชัดเจน เช่น `Tudv`, `uszainivasnis`, `sHadiwav`, `4@37%8_)`
2. **ข้อความที่เกิดจากการจัดหมวด/วิเคราะห์อัตโนมัติ (Algorithmic Enrichment):**
   - แหล่งที่มา: ฟิลด์ `category` ใน `FORENSIC_CHAT_EVIDENCE_DATA.json`, ฟิลด์ `typology` ใน `TIMELINE_11D_EVIDENCE_DATA.json`
   - ลักษณะ: ข้อความวิเคราะห์ที่เกิดจากเงื่อนไข Regex / คีย์เวิร์ดในโค้ด (เช่น ตรวจพบคำว่า "น้ำหอมแตก" ➔ กำหนดหมวดเป็น `THIRD_PARTY_COERCION`)
3. **ข้อความที่เขียนไว้ล่วงหน้าในสคริปต์ (Pre-baked / Expert Curated):**
   - แหล่งที่มา: อาร์เรย์ `counts` ใน `build_court_dossier_smart_cropped.py`, อาร์เรย์ `defendants` ใน `agent4_court_indictment_packager.py`, และ `smoking_gun_catalog` ใน `agent3_forensic_linguistics_miner.py`
   - ลักษณะ: ข้อความคำบรรยายฟ้องร้องภาษากฎหมายสละสลวย, การอ้างอิงมาตรา ป.อ., ป.พ.พ., คำพิพากษาฎีกา ซึ่งเขียนขึ้นโดยนักกฎหมาย/ผู้จัดทำสำนวน มิได้เกิดจากการอ่านของ AI อัตโนมัติ

## 4. เสถียรภาพและความคงที่ของรหัสระบุ (ID Stability Matrix)

| ชื่อฟิลด์ ID | แหล่งที่สร้าง (Origin) | พฤติกรรมเมื่อรันใหม่ (Re-run Stability) | ข้อควรระวัง (Caution) |
| :--- | :--- | :--- | :--- |
| **`sha256` / `md5`** | ไบนารีของไฟล์ภาพต้นฉบับ | **คงที่ 100% (Deterministic)** | หากไฟล์ถูกบีบอัด เซฟทับ หรือแก้ไขแม้แต่ 1 ไบต์ ค่าจะเปลี่ยนทันที |
| **`node_id` / `nid`** | ลำดับการเรียงไฟล์ใน `build_ssot_viewer.py` | **กึ่งคงที่ (Semi-stable)** | อิงตามลำดับ Natural Sort ของโฟลเดอร์ หากมีไฟล์ใหม่แทรก ลำดับจะเลื่อน |
| **`ref_no` (Ref ID)** | ตัวเลขอ้างอิงสลิปธนาคาร (เช่น `20250901...`) | **คงที่ 100%** | เป็นเลขอ้างอิงของระบบธนาคารจริง ใช้เป็นกุญแจเชื่อมโยงข้ามระบบได้ดีที่สุด |
| **`count_no`** | ลำดับกรรมในสำนวนคดี (กรรมที่ ๑ ถึง ๓๐) | **คงที่ตามชุดสำนวน** | ถูกผูกโยงตามลำดับเหตุการณ์ 30 รายการใน `EVIDENCE_COUNTS_30.json` |
| **`exhibit_no`** | หมายเลขพยานเอกสารศาล (หมาย จ.๑ ถึง จ.๓๐) | **คงที่** | สร้างโดย Agent 6 ผูก 1:1 กับ `count_no` |
| **`candidate_id` / `SG-01..08`** | รหัสจุดตายคดีใน Agent 3 | **คงที่ตามโครงสร้างสคริปต์** | เป็นรหัส Hardcoded ใน `smoking_gun_catalog` |
